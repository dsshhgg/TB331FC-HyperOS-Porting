# TB331FC × HyperOS 4 移植可行性报告

> **对象**：把小米 HyperOS 4（`yupei`，Android 17）移植到联想小新平板 2024（**TB331FC**，底包 ZUI）
> **日期**：2026-10
> **性质**：**只读解析 + 对比**。全程未执行任何 `fastboot flash`、未写入任何分区、未改动原厂固件。
> **一句话结论**：**完整移植不可行**；否决项是 **GKI/KMI 跨代** 与 **SoC 代际不同**。
> 体积与分区布局**不是**否决项（经复核可通过重排 super 逻辑分区解决）。

本报告的每一项数据都来自**对原厂二进制/镜像的直接解析**，不采信任何中间文档的转述。

| 侧 | 系统 | 厂商 |
|----|------|------|
| ZUI（TB331FC） | 14 / SDK 34 | 13 / SDK 33 |
| HyperOS（yupei） | 17 / SDK 37 | 15 / SDK 35 |
| **差距** | **+3 个大版本** | **+2 个大版本** |

带来的破坏性变更（非穷举）：

| 变更面 | 影响 |
|--------|------|
| API / 权限模型 | system_server 与 vendor HAL 的 AIDL 接口版本对不上 |
| VNDK / APEX | ZUI vendor 是 VNDK 33；HyperOS 系统侧期望 VNDK 35+ 的 HAL 形态 |

| SELinux | 策略域大量新增/改名，`precompiled_sepolicy` 不通用 |
| BPF / eBPF（`bpfloader`） | **与内核版本强绑定**，Android 17 的 BPF 程序无法在 5.15 内核上加载 |

> 即便前三条被绕过，**BPF 这一条也足够让 Android 17 的框架起不来**（详见 §5）。

## 5. GKI / KMI 兼容性（一票否决）

| 检查项 | ZUI | HyperOS | 结果 |
|--------|-----|---------|------|
| 内核主版本 | 5.15.123 | 6.6.118 | ❌ |
| GKI 生成线 | `android13-5.15` | `android15-6.6` | ❌ |
| 模块 vermagic | `5.15.123-android13-8-...` | `6.6.118-android15-8-...` | ❌ |
| 符号表 / CRC | 两套 | 两套 | ❌ |

**GKI/KMI 的兼容承诺只在同一条 `androidXX-<ver>` 生成线内成立。**
`android13-5.15` 与 `android15-6.6` 是两条独立的内核产品线：

- 用 ZUI 内核 + HyperOS `system_dlkm`/`vendor_dlkm` → 模块**加载即失败**（vermagic/CRC 不符）
- 用 HyperOS 内核 + ZUI vendor → 设备树、固件节点、驱动全部绑 SM6225，**点不亮屏**
- 反向亦然

**并且**：Android 17 的系统框架依赖内核里的 BPF 程序与 `bpfloader` 映射表，这些是按内核版本
编译进 system 的。5.15 内核 + Android 17 框架属于**官方从未支持的组合**，表现是
`init` 阶段直接失败（无法开机），不是「功能残缺」。

> 这一条是**独立于体积、独立于文件系统**的硬否决项。

## 7. 关于「空间硬约束」的复核（结论：**不是否决项**）

早期文档判定「HyperOS 系统侧 9.26 GiB > system_a 5.79 GiB，物理装不下」。复核后**两个数字都不准**，
且这个约束**可以通过重排 super 逻辑分区解决**：

| 项 | 数值 | 来源 |
|----|------|------|
| HyperOS 系统侧合计 | **7.96 GiB** | payload 清单字节数精确求和 |
| ZUI `system_a` 当前尺寸 | **5.12 GiB** | liblp 元数据 |
| ZUI super 物理容量 | **12.00 GiB** | liblp block device |
| `qti_dynamic_partitions_a` group 上限 | **11.99 GiB** | liblp group |
| slot A 已用 | **6.79 GiB** | liblp + extents |
| slot B 已用 | **0 B** | 全部逻辑分区 sectors = 0 |
| **super 内可用余量** | **≈ 5.20 GiB** | 11.99 − 6.79 |

**重排可行性验算**（保留 ZUI 硬件侧，只换成 HyperOS 系统侧）：

```
保留 ZUI：vendor_a 0.6345 + odm_a 0.0013 + vendor_dlkm_a 0.0549 + system_dlkm_a 0.0004
        = 0.691 GiB
放入 HyperOS：system + system_ext + product + mi_ext + mi_product
        = 7.962 GiB
合计   = 8.653 GiB   ≤ 11.99 GiB（group 上限）   ✅ 装得下
余量   ≈ 3.34 GiB
```

实现方式（任一）：`fastboot resize-logical-partition`（group 有余量时可用）、
或重打包 `super.img`（`lpmake`）后经 9008 线刷。**不需要改 GPT，不需要动物理分区表。**

> **所以「装不下」是工程问题，不是原理问题。**
> 真正让这条路走不通的仍然是 §5 的 KMI 与 §6 的硬件栈。
> （顺带：§2.4 已证明同一台机器的逻辑分区尺寸在联想两次打包中就不同，说明分区尺寸本就是可调的。）

## 8. 综合判定

| 维度 | 评级 | 依据 |
|------|------|------|
| Android 版本差距 | ❌ | 系统 14→17（+3），vendor 13→15（+2） |
| **GKI / KMI** | ❌ **否决** | `android13-5.15` vs `android15-6.6` |
| **SoC / 固件代际** | ❌ **否决** | `bengal`(SM6225) vs `oryon`(骁龙 8 Elite 级) |
| vendor HAL（显示/触摸/音频/传感器） | ❌ | 四层全不同，无一可移植 |
| 分区空间 | ⚠️ 可解 | super 余量 5.20 GiB，重排后 8.65 GiB ≤ 11.99 GiB |
| 文件系统 | ⚠️ 可解 | EXT4 ↔ EROFS 可转换 |
| Treble | ✅ | `ro.treble.enabled=true`，A/B + GKI 5.15，符合 GSI 画像 |

### 结论：**不可行**

指「用 `yupei` HyperOS 4（A17 / android15-6.6）的 system/product/system_ext 直接替换、
底包只留 ZUI 的 boot/vendor」这条**完整移植**路径。

按致命程度排序：

1. **KMI 不兼容**（android13-5.15 vs android15-6.6）：没有共同内核 ABI，模块无法加载；
   且 Android 17 框架的 BPF 程序与内核版本强绑定。
2. **SoC 代际不同**（SM6225 vs 骁龙 8 Elite 级 / Oryon）：vendor、固件链、设备树不可互换。
3. **四大硬件栈全不对**（显示 / 触摸 / 音频 / 传感器）：即使内核问题被绕过，也没有可用的驱动。
4. **API 跨 3 代**：init / SELinux / VNDK / HAL 接口连锁崩。

> 补充：**「只换系统侧、保留 ZUI 内核」这条折中路线同样不成立** ——
> 它仍然要求 Android 17 的框架跑在 5.15.123-android13 内核上，属于官方从未支持的组合。

## 9. 推荐替代路线

| 路线 | 做法 | 预期 | 难度 |
|------|------|------|------|
| **A. GSI（推荐）** | ZUI 全底（boot / init_boot / vendor_boot / dtbo / vendor / odm / 固件全保留）+ **HyperOS/AOSP arm64-ab GSI** 替换 system | 有类 HyperOS 体验，硬件由 ZUI vendor 驱动 | 中 |
| **B. 降级源包** | 找与 `android13-5.15` **同代 KMI** 的平板包（HyperOS 1.x / Android 13–14）再拼 | 兼容性最好 | 中高 |
| **C. 既有验证包** | 社区已有的 TB331FC 专包（如酷安 weiPluto 的 HyperOS 2.0 包，内置 KSU） | 已有可刷产物 | 低 |
| **D. 完整移植 yupei A17** | 本报告路径 | **不可行** | — |

### 对路线 A 的补充

- TB331FC 满足 GSI 画像：`ro.treble.enabled=true`、A/B、GKI `android13-5.15`。
- 仍须：`fastboot -w`（清数据）、保留 ZUI 的 boot / vendor_boot / vendor / odm、关闭 AVB 验证。
- 手写笔 / 相机 / 杜比仍依赖 ZUI vendor + 属性与脚本修补（可复用既有 `_boot_fix` 经验）。
