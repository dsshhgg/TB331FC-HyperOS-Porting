# TB331FC × HyperOS 4 移植可行性报告

> **对象**：把小米 HyperOS 4（`yupei`，Android 17）移植到联想小新平板 2024（**TB331FC**，底包 ZUI）
> **日期**：2026-10
> **性质**：**只读解析 + 对比**。全程未执行任何 `fastboot flash`、未写入任何分区、未改动原厂固件。
> **一句话结论**：**完整移植不可行**；否决项是 **GKI/KMI 跨代** 与 **SoC 代际不同**。
> 体积与分区布局**不是**否决项（经复核可通过重排 super 逻辑分区解决）。

---

## 0. 结论速览

| 维度 | ZUI 底包（TB331FC） | HyperOS 源包（yupei） | 判定 |
|------|---------------------|------------------------|------|
| 系统侧 Android | **14**（SDK 34） | **17**（SDK 37） | ❌ 跨 3 个大版本 |
| vendor 侧 Android | **13**（SDK 33） | **15**（SDK 35） | ❌ 跨 2 个大版本 |
| 内核 | `5.15.123-android13-8` | `6.6.118-android15-8` | ❌ **否决** |
| GKI KMI | **android13-5.15** | **android15-6.6** | ❌ **否决** |
| SoC / 平台 | `bengal`（SM6225 / 骁龙 685） | `oryon` CPU 核（骁龙 8 Elite 级） | ❌ **否决** |
| 分区文件系统 | EXT4 | EROFS（lz4hc） | ⚠️ 可转换，非否决 |
| 系统侧体积 | system_a 5.12 GiB | 系统侧合计 7.96 GiB | ⚠️ 可通过重排 super 容纳 |
| Treble | `ro.treble.enabled=true` | — | ✅ 具备 GSI 条件 |
| vendor API level | `ro.board.api_level=33` | `ro.llndk.api_level=202604` | ❌ 相差约 3 年接口面（见 §8A） |

**路线结论**：

- ❌ **完整移植**（换 kernel / vendor / system）—— 不可行（§5 + §6 双否决）
- ⚠️ **保留 ZUI 内核与 vendor、只换 system 侧** —— **超出官方兼容包线，但未被证否**；
  真正的关卡是 vendor API level / VNDK / BPF（§8A），**只能实测判定**
- ✅ **推荐**：先做 §8A.5 的最小代价验证（现成 A 档镜像可用于 S1）；
  若失败再走 **GSI** 或**降级到与 `android13-5.15` 同代的源包**

## 4. Android 版本差距

| 侧 | 系统 | 厂商 |
|----|------|------|
| ZUI（TB331FC） | 14 / SDK 34 | 13 / SDK 33 |
| HyperOS（yupei） | 17 / SDK 37 | 15 / SDK 35 |
| **差距** | **+3 个大版本** | **+2 个大版本** |

带来的破坏性变更（非穷举）：

| 变更面 | 影响 |
|--------|------|
| API / 权限模型 | system_server 与 vendor HAL 的 AIDL 接口版本对不上 |
| VNDK / APEX | ZUI vendor 是 VNDK 33；HyperOS 系统侧期望 VNDK 35+ 的 HAL 形态 |
| init / `.rc` 语法 | `first_stage_mount`、`apex`、`dm-verity` 行为变化 |
| SELinux | 策略域大量新增/改名，`precompiled_sepolicy` 不通用 |
| BPF / eBPF（`bpfloader`） | **与内核版本强绑定**，Android 17 的 BPF 程序无法在 5.15 内核上加载 |

> 即便前三条被绕过，**BPF 这一条也足够让 Android 17 的框架起不来**（详见 §5）。

## 5. GKI / KMI 兼容性（一票否决）

| 检查项 | ZUI | HyperOS | 结果 |
|--------|-----|---------|------|
| 内核主版本 | 5.15.123 | 6.6.118 | ❌ |
| GKI 生成线 | `android13-5.15` | `android15-6.6` | ❌ |
| 模块 vermagic | `5.15.123-android13-8-...` | `6.6.118-android15-8-...` | ❌ |
| 符号表 / CRC | 两套 | 两套 | ❌ |

**GKI/KMI 的兼容承诺只在同一条 `androidXX-<ver>` 生成线内成立。**
`android13-5.15` 与 `android15-6.6` 是两条独立的内核产品线：

- 用 ZUI 内核 + HyperOS `system_dlkm`/`vendor_dlkm` → 模块**加载即失败**（vermagic/CRC 不符）
- 用 HyperOS 内核 + ZUI vendor → 设备树、固件节点、驱动全部绑 SM6225，**点不亮屏**
- 反向亦然

**并且**：Android 17 的系统框架依赖内核里的 BPF 程序与 `bpfloader` 映射表，这些是按内核版本
编译进 system 的。5.15 内核 + Android 17 框架属于**官方从未支持的组合**，表现是
`init` 阶段直接失败（无法开机），不是「功能残缺」。

> 这一条是**独立于体积、独立于文件系统**的硬否决项。

## 7. 关于「空间硬约束」的复核（结论：**不是否决项**）

早期文档判定「HyperOS 系统侧 9.26 GiB > system_a 5.79 GiB，物理装不下」。复核后**两个数字都不准**，
且这个约束**可以通过重排 super 逻辑分区解决**：

| 项 | 数值 | 来源 |
|----|------|------|
| HyperOS 系统侧合计 | **7.96 GiB** | payload 清单字节数精确求和 |
| ZUI `system_a` 当前尺寸 | **5.12 GiB** | liblp 元数据 |
| ZUI super 物理容量 | **12.00 GiB** | liblp block device |
| `qti_dynamic_partitions_a` group 上限 | **11.99 GiB** | liblp group |
| slot A 已用 | **6.79 GiB** | liblp + extents |
| slot B 已用 | **0 B** | 全部逻辑分区 sectors = 0 |
| **super 内可用余量** | **≈ 5.20 GiB** | 11.99 − 6.79 |

> **证据局限（须知）**：以上 super 布局来自**原厂线刷包**（`TB331FC_ZUI_16.0.544\image`），
> 代表「干净线刷后」的布局。设备**当前实际**的 super 布局可能被历史刷机改变，
> 本次无设备连接（`adb devices` / `fastboot devices` 均为空），**未做在线核对**。
> 执行任何重排前必须先读设备当时的 LP 元数据。

**重排可行性验算**（保留 ZUI 硬件侧，只换成 HyperOS 系统侧）：

```
保留 ZUI：vendor_a 0.6345 + odm_a 0.0013 + vendor_dlkm_a 0.0549 + system_dlkm_a 0.0004
        = 0.691 GiB
放入 HyperOS：system + system_ext + product + mi_ext + mi_product
        = 7.962 GiB
合计   = 8.653 GiB   ≤ 11.99 GiB（group 上限）   ✅ 装得下
余量   ≈ 3.34 GiB
```

实现方式（任一）：`fastboot resize-logical-partition`（group 有余量时可用）、
或重打包 `super.img`（`lpmake`）后经 9008 线刷。**不需要改 GPT，不需要动物理分区表。**

> **所以「装不下」是工程问题，不是原理问题。**
> 真正让这条路走不通的仍然是 §5 的 KMI 与 §6 的硬件栈。
> （顺带：§2.4 已证明同一台机器的逻辑分区尺寸在联想两次打包中就不同，说明分区尺寸本就是可调的。）

## 8. 综合判定

| 维度 | 评级 | 依据 |
|------|------|------|
| Android 版本差距 | ❌ | 系统 14→17（+3），vendor 13→15（+2） |
| **GKI / KMI** | ❌ **否决** | `android13-5.15` vs `android15-6.6` |
| **SoC / 固件代际** | ❌ **否决** | `bengal`(SM6225) vs `oryon`(骁龙 8 Elite 级) |
| vendor HAL（显示/触摸/音频/传感器） | ❌ | 四层全不同，无一可移植 |
| 分区空间 | ⚠️ 可解 | super 余量 5.20 GiB，重排后 8.65 GiB ≤ 11.99 GiB |
| 文件系统 | ⚠️ 可解 | EXT4 ↔ EROFS 可转换 |
| Treble | ✅ | `ro.treble.enabled=true`，A/B + GKI 5.15，符合 GSI 画像 |

### 结论：**不可行**

指「用 `yupei` HyperOS 4（A17 / android15-6.6）的 system/product/system_ext 直接替换、
底包只留 ZUI 的 boot/vendor」这条**完整移植**路径。

按致命程度排序：

1. **KMI 不兼容**（android13-5.15 vs android15-6.6）：没有共同内核 ABI，模块无法加载；
   且 Android 17 框架的 BPF 程序与内核版本强绑定。
2. **SoC 代际不同**（SM6225 vs 骁龙 8 Elite 级 / Oryon）：vendor、固件链、设备树不可互换。
3. **四大硬件栈全不对**（显示 / 触摸 / 音频 / 传感器）：即使内核问题被绕过，也没有可用的驱动。
4. **API 跨 3 代**：init / SELinux / VNDK / HAL 接口连锁崩。

> ⚠️ **本报告 2026-10 初版在此处写过「只换系统侧、保留 ZUI 内核这条折中路线同样不成立」。
> 该表述过于绝对，且当时未做机制级取证。已由下节 §8A 取代。**

## 8A. 关于「保留原厂内核、只换系统侧」路线（重要更正）

> 触发：用户指出本方案本就是用原厂内核，不应被判死。以下为针对该路线的**机制级取证**。

### 8A.1 这条路线确实解决掉的（我此前高估了它的问题）

| 原报告中的否决项 | 在本路线下 | 说明 |
|------------------|-----------|------|
| KMI / vermagic 混装模块 | ✅ **不存在** | 不换内核、不换 vendor_dlkm，模块全是 ZUI 自己的 |
| SoC / 固件链不可互换 | ✅ **不存在** | vendor / odm / 固件全部保留 ZUI |
| 显示/触摸/音频/传感器驱动差异 | ✅ **不存在** | 这四层根本不动，ZUI HAL 原样运行 |
| 系统侧体积超 system_a | ✅ 可解 | super 余量 5.20 GiB（§7） |

**所以 §6 的硬件栈分析和 §5 的「模块不可混装」部分，对本路线不构成否决。**

### 8A.2 我此前的一个事实性错误（重要）

初版暗示「Android 17 就必须配 6.18 代 GKI」。**这是错的。**

`yupei` 自己就是 **Android 17 跑在 `android15-6.6` GKI 上**（内核 banner 实测），
而 AOSP 官方 Android 17 的 GKI 生成线是 `android17-6.18`（[AOSP GKI 发布构建索引](https://source.android.google.cn/docs/core/architecture/kernel/gki-release-builds)）。

→ **Android 版本与 GKI 代际是解耦的**，OEM 可以让新 Android 跑在旧 GKI 上。
我此前把「A17 框架必须配 A17 内核」当成前提，不成立。

### 8A.3 但这条路线**不解决**的：system ↔ vendor 的**用户态契约**

保留内核，只换 system，意味着 **A17 的 system 用户态**要去驱动 **A13 的 vendor 用户态**。
这里有三道已取证的关卡：

#### 关卡 1：vendor API level（**最硬**）

| 侧 | 属性 | 实测值 |
|----|------|--------|
| ZUI vendor | `ro.board.api_level` | **33** |
| ZUI vendor | `ro.board.first_api_level` | **33** |
| ZUI vendor | `ro.product.first_api_level` | **33** |
| ZUI vendor | `ro.vndk.version` | **33** |
| HyperOS A17 system | `ro.llndk.api_level` | **202604** |

- `ro.llndk.api_level` 是**系统侧**声明的 LLNDK 接口面；`ro.vendor.api_level` 是 init 在启动时
  从 `ro.board.api_level` / `ro.board.first_api_level` / `ro.product.first_api_level` 算出来的。
- **A17 的 `init` 二进制里确实带有这套逻辑**：实测其字符串含
  `ro.vendor.api_level`、`ro.board.api_level`、`ro.board.first_api_level`、`ro.product.first_api_level`
  以及报错串 **`Unexpected vendor api level for `** —— 说明 vendor API level 在 A17 里是一等兼容性输入。
- AOSP 规则：`ro.board.api_level` 若低于 `202404`（旧数字格式），则
  `ro.vendor.api_level = min(ro.board.first_api_level, ro.product.first_api_level)`；本例 = **33**。
- 而 Google 对系统侧/GSI 的公开要求是 **vendor API level 需达到该 Android 版本的 LLNDK 门槛**
  （Android 15 起要求 `202404`+，逐版本抬升；见
  [AOSP 供应方 API 级别](https://source.android.google.cn/docs/core/architecture/api-flags)、
  [Android GSI 说明](https://developer.android.google.cn/topic/generic-system-image)）。
  ZUI 的 33 与 A17 的 202604 相差约 **3 年**的接口面。

> **这一关卡与内核无关**，因此「用原厂内核」绕不过去。它也解释了为什么社区惯例是
> 「新系统 + 同代或次代 vendor」，而不是「新系统 + 三代前 vendor」。

#### 关卡 2：VNDK 被移除

| 侧 | `/system/apex/` 中的 VNDK |
|----|---------------------------|
| ZUI（A14） | **有** `/system/apex/com.android.vndk.current/`（含 `vndkcore.libraries.34.txt`、`vndksp.libraries.34.txt`、`llndk.libraries.34.txt` …） |
| HyperOS（A17） | **没有任何 `com.android.vndk.*`** —— 实测 `/system/apex` 下 36 个 APEX 全为其它模块 |

而 ZUI 的 vendor HAL 是 **HIDL + VNDK 世代**的产物。实测其 `DT_NEEDED`：

```
android.hardware.audio.service_64
    libcutils libbinder libbinder_ndk libhwbinder libhidlbase liblog libutils libhardware ...
vendor.qti.hardware.display.composer-service   (38 个依赖)
    libhidlbase libhardware libhardware_legacy libutils libcutils libsync
    libqdMetaData libgralloctypes libgrallocutils libgralloc.qti
    android.hardware.graphics.composer@2.1/2.2/2.3/2.4.so
    vendor.qti.hardware.display.composer@3.0.so ...
android.hardware.sensors@2.1-service.multihal
    libhidlbase libbase libcutils libutils libfmq android.hardware.sensors@2.0/2.1.so ...
vendor.dolby.hardware.dms@2.0-service
    libhidlbase libutils vendor.dolby.hardware.dms@2.0(-impl).so ...
```

好消息（**已从原镜像核实**）：A17 的 `/system/lib64` **仍然提供** `libhidlbase.so`、`libhidltransport.so`、
`libhwbinder.so`、`libutils.so`、`libhardware.so`、`libhardware_legacy.so`、`libion.so`、`libsync.so`、
`libgralloctypes.so`、`libvndksupport.so` —— 即 HIDL/LLNDK 运行时并未消失，A17 只是**不再以 VNDK APEX 形式交付**。

> ⚠️ **自我更正**：初版报告曾据 `work/trees/` 抽取树判定这些库「缺失」。
> 那是**前期抽取树不完整**造成的假象 —— 同一批文件在原镜像里都在。
> 后续所有结论均已改从**原镜像（sha256 已校验）**取证。
> 这也说明 `work/trees/**` 不可作为完整性依据，只能当参考。

**所以关卡 2 是「风险」而非「已证实的死路」**：A17 有没有为 VNDK-33 的 vendor 保留足够
LLNDK 面，只能实测。

#### 关卡 3：BPF 程序覆盖（**已证实缺失，但大概率非致命**）

A17 的 system 会随包下发一批 BPF 程序，`netbpfload.rc` 里明确：

```
exec_start bpfloader
wait_for_prop bpf.progs_loaded 1
# (this will hang if bpfloader fails)
```

逐符号核对两侧内核（直接读 raw kernel 字符串）：

| 符号 | ZUI 5.15.123-android13 | yupei 6.6.118-android15 | 相关 BPF 程序 |
|------|------------------------|--------------------------|----------------|
| `shmem_swapin_folio` | ❌ **无**（只有 `shmem_swapin_page`） | ✅ 有 | `MiuiMmPerf.o` → `kprobe/shmem_swapin_folio` |
| `bpf_iter_ksym` | ❌ **无** | ✅ 有 | `MiuiBpfGplDefineset.o` → `iter/ksym` |
| `mm_calculate_totalreserve_pages` | ❌ **无** | ✅ 有 | `bpfMemEvents.bpf` |
| `android_vendor_lmk` | ❌ **无** | ✅ 有(稀少) | `bpfMemEvents.bpf` |
| `enter_fd_install` | ❌ 无 | ❌ 无 | `MiuiBpfDefineset.o` |
| `gpu_work_period` | ❌ 无 | ❌ 无 | `gpuWork.bpf` |
| `damon_aggregated` / `cgroup_attach_task` / `vfs_unlink` / `__bpf_trace` / BTF | ✅ 有 | ✅ 有 | 其余程序 |

即：**A17 至少 4 个 BPF 程序依赖 ZUI 内核里不存在的符号**（且 ZUI A14 只下发 4 个 BPF 对象，
A17 下发 16+ 个）。

**但是**：A17 的 `bpfloader` 二进制里带 **内核版本门控**与**跳过语义**：

```
 min_kver:      max_kver:      kvers:
 Skipping load of      skipping program      skipping map      Skip loading
 not found, ignoring
```

且部分对象确实携带 `min_kver` / `max_kver` 元数据（实测 `MiuiBpfDefineset.o`、`MiuiBpfTimeInState.o`、
`tclimiter.o` 有；`MiuiMmPerf.o`、`bpfMemEvents.bpf` 等**没有**）。

→ 结论：**内核版本不满足的程序预计被跳过并记日志，而非让 init 挂死**。代价是丢失
LMK / 内存统计 / 调度观测等增强功能，通常不直接导致黑屏。
（此项为**推断**，不是实测结论。）

### 8A.4 对该路线的诚实评级

| 维度 | 评级 |
|------|------|
| 是否「不可能」 | **不是**。它绕开了本报告 §5 的模块混装与 §6 的硬件栈问题 |
| 是否在官方支持包线内 | **否**。vendor API level 33 vs A17 期望 202604；kernel 5.15 vs A15+ 系统侧基线 6.6 |
| 最可能的失败点 | 关卡 1（vendor API level / LLNDK 面）与关卡 2（VNDK 缺失） |
| 失败表现预期 | init / pre-zygote 阶段拒绝或 bootloop；或能起但 HAL 大面积起不来 |
| 能否靠静态分析定论 | **不能**。这三关都是运行期行为 |

**因此：本报告把「结论」修正为 —— 完整移植（含换 vendor/内核）不可行；
「保留 ZUI 内核与 vendor、只换系统侧」属于「超出官方兼容包线、但未被证否」的路线，
唯一的判定方式是实测。**

### 8A.5 若要走这条路，最小代价的验证方案

```text
前置（缺一不可）
  1. 全分区备份：boot/init_boot/vendor_boot/dtbo/vbmeta/vbmeta_system/recovery
                  + super 内全部分区 + persist + lenovocust      → scripts/backup_partitions.ps1
  2. 确认 9008 可用（prog_firehose_sm6225_ddr.elf）与救砖包在手
  3. 记录当前 slot / unlock 状态

试验顺序（每步只前进一步，失败即回滚）
  S1  只刷 system_a（换成 A 档精简镜像），保留 boot/init_boot/vendor_boot/dtbo/vbmeta
      → 观察：能否过 init → 是否卡在 wait_for_prop bpf.progs_loaded
  S2  若 S1 卡 BPF：核对 dmesg/logcat 中 bpfloader 的 skip 记录
  S3  若 S1 过 init 但黑屏：查 hwservicemanager / composer / sensors 服务是否起来
      → 这是关卡 1/2（vendor API level / VNDK）的直接证据
  S4  仍失败则判定该路线在 TB331FC 上不可用，转 §9 路线 A（GSI）或 B（降级源包）

风险
  - 首次试刷必然清数据
  - 失败可能落到 9008 恢复
  - 未经确认不得执行（本项目硬约束）
```

> 但**注意**：该镜像是在 `work/trees/`（已证实不完整）基础上 debloat + 打包的，
> **打包前应先从原镜像重新解包并校验**，否则可能缺文件。

## 9. 推荐替代路线

| 路线 | 做法 | 预期 | 难度 |
|------|------|------|------|
| **A. GSI（推荐）** | ZUI 全底（boot / init_boot / vendor_boot / dtbo / vendor / odm / 固件全保留）+ **HyperOS/AOSP arm64-ab GSI** 替换 system | 有类 HyperOS 体验，硬件由 ZUI vendor 驱动 | 中 |
| **B. 降级源包** | 找与 `android13-5.15` **同代 KMI** 的平板包（HyperOS 1.x / Android 13–14）再拼 | 兼容性最好 | 中高 |
| **C. 既有验证包** | 社区已有的 TB331FC 专包（如酷安 weiPluto 的 HyperOS 2.0 包，内置 KSU） | 已有可刷产物 | 低 |
| **D. 完整移植 yupei A17** | 换内核 + vendor + system | **不可行** | — |
| **E. 保留 ZUI 内核/vendor，只换 system 侧** | 即用户主张的「用原内核」；见 §8A | **未证否**；关卡为 vendor API level / VNDK / BPF | 中高（需实测） |

> 路线 E 与路线 A 的区别：A 用**通用** system（GSI，按 vendor API level 门控设计，Google 会明确拒绝过旧的 vendor）；
> E 用**为另一台机器定制的** system（HyperOS 4），兼容性预期不优于 GSI，但可自带小米框架。
> **建议先花最小代价实测 E（§8A.5 的 S1），再决定是否转 A/B。**

### 对路线 A 的补充

- TB331FC 满足 GSI 画像：`ro.treble.enabled=true`、A/B、GKI `android13-5.15`。
- 仍须：`fastboot -w`（清数据）、保留 ZUI 的 boot / vendor_boot / vendor / odm、关闭 AVB 验证。
- 手写笔 / 相机 / 杜比仍依赖 ZUI vendor + 属性与脚本修补（可复用既有 `_boot_fix` 经验）。
