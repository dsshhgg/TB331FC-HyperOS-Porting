# 实验准备记录：HyperOS 4.0（A17）「去 tz_log_dlkm + 关 qseelogd」双补丁版

- 日期：2026-10-20（构建与静态验证）｜设备未连接，**尚未刷入**
- 依据：`E:\rom\docs\澎湃4可行性结论_2026-10-18.md` §10.1 **#2b（优先）** 与 **#2**
- 上游结论：§9.1 把 A17 判死的原因是 `tz_log_dlkm` 在内核态非法 MMIO；§10.1 **#2b** 因此列为
  当前最有希望的 A17 路线。所以本轮不改内核、不换 boot 链，只做**最小干预**：让那个模块不加载
  + 让唯一会去读 `/proc/tzdbg` 的守护进程不启动。

---

## 1. 两个补丁

| # | 分区 | 改动 | 手法 | 实测差异 |
|---|---|---|---|---|
| #2b | `vendor_dlkm` | `/lib/modules/modules.load` 里 `tz_log_dlkm.ko` 那一行 → 14 个空格 | **原地改数据块**（尺寸不变） | 与 stock 逐字节比对：**仅 14 字节不同** |
| #2  | `system_ext`  | `/etc/build.prop` 的 `persist.sys.qseelogd=true` → `false` | 重打包整镜像（v2） | 与 v1 差异即该属性 |

### 1.1 为什么「抹掉 modules.load 里那一行」就够

`/vendor/bin/vendor_modprobe.sh` 的加载路径是：

```sh
load_modules=$(cat ${dir}/modules.load | grep -w -v ${blocklist_expr} | ...)
for m in ${load_modules}; do insmod ${m}; done
```

也就是说：**模块是否加载，完全由 `modules.load` 的文本决定**，与 `.ko` 文件是否存在无关。
`tz_log_dlkm` 不在 blocklist 里、也不被任何其他模块依赖（`modules.dep` 依赖表为空），
所以把这一行变成空白行后，`echo` 词分割时它自然消失，`insmod` 永远不会执行，
`/proc/tzdbg` 也就永远不会被创建 —— 崩溃链（`tzdbg_fs_read+0x88 → __memcpy_fromio+0xb0
→ FAR 0xffffffff96000210`）在结构上不可达。

**没有选择删文件/改名**，因为：删文件会动目录项、inode 位图与 xattr；而抹一行只碰一个数据块。

### 1.2 为什么「原地改 14 字节」不会破坏文件系统

- `modules.load` 只有 3,569 B，**小于一个 4096 B 块** → 重写只落在一个数据块上，不碰 extent 树、
  不碰块位图、不碰 group descriptor；
- 镜像 `ro_compat=0x407B`，**没有 `metadata_csum`（0x400）** → 数据块没有校验和可被打破
  （`compat=0x28` 的 GDT_CSUM 只覆盖元数据）；
- 改后 inode 的 size / blocks / mode(100644) / uid:gid(0:0) /
  `security.selinux=u:object_r:vendor_file:s0` 以及 AVB footer **全部字节不变**。

### 1.3 为什么只改 `vendor_dlkm`、不改 `vendor_boot` 里的 ramdisk

`vendor_boot` 的 vendor_ramdisk 里**确实有** `lib/modules/tz_log_dlkm.ko` 这个文件（48984 B），
但它自己的 `lib/modules/modules.load`（1280 B，80 行，第一阶段的子集）里**没有** `tz_log`，
`modules.blocklist` 里也没有 —— 也就是说第一阶段的 ramdisk 从不加载它，
真正会 insmod 它的只有 `vendor_dlkm` 那份 218 行的 `modules.load`。所以**不需要碰 `vendor_boot`**，
避免了动启动链的风险。

### 1.4 `vendor_dlkm` 有两个版本，必须匹配当前 build

| flavour | 源镜像 | 字节 | stock MD5 | 补丁后 MD5 |
|---|---|---|---|---|
| zui16 | `...\TB331FC_ZUI_16.0.544\image\super_8.img` | 58,933,248 | `FFDA361047139AAA88AB3EE0B00AD00F` | `73D487C44D0FB7AE80A401376572E6DE` |
| zui17 | `E:\rom\release\TB331FC-rollback-zui17\images\vendor_dlkm.img` | 59,342,848 | `40F83F9269FB79B6A9EB66C6376370E4` | `AF8FDD00901CD40A70417EB27F12CCEB` |

两者 superblock 参数相同（block 4096 / inode 256 / ro_compat 0x407B），差别是 ZUI17 多
`smsc.ko`/`smsc75xx.ko`/`smsc95xx.ko` 三个 usb-net 模块，且 `tz_log_dlkm.ko` 本体字节不同。
**混用会把另一代 build 的 vendor_dlkm 塞进正在启动的 vendor**，所以刷写脚本默认走
`-FromDevice`（dd 设备自己那份、原地打补丁再刷回），离线镜像只在拿不到设备时用，且强制哈希闸门。

## 4. 设备接上后的刷写流程

```powershell
# 0) 先空跑，确认闸门、槽位、resize 计划都对（不动设备）
powershell -File flash_a17_notz.ps1 -FromDevice -Wipe

# 1) 真刷（推荐 -FromDevice：补丁打在设备自己那份 vendor_dlkm 上）
powershell -File flash_a17_notz.ps1 -FromDevice -Wipe -Execute

# 设备拿不到时的离线路线（哈希闸门会拦 flavour 不匹配）
powershell -File flash_a17_notz.ps1 -VendorDlkm "E:\rom\port\hyperos\out\vendor_dlkm_a_notz_zui17.img" -Wipe -Execute
```

脚本内部的顺序：preflight（`getvar unlocked` / slot）→ **先缩后扩** logical partition
（system 缩到 1.75 GB 级、product/system_ext 扩到镜像大小）→ 刷四个分区 → 提醒 wipe → reboot。
**全程不碰** boot / init_boot / vendor_boot / dtbo / vbmeta / vbmeta_system / super header /
vendor / odm / system_dlkm / persist（`-Wipe` 除外）。

### 回滚

```powershell
powershell -File flash_a17_notz.ps1 -Rollback -Wipe -Execute
```
回滚按 `$BackupDir` 里的现网 dump 优先、否则用 ZUI16 stock（`super_4/3/6/8`，MD5 已写进脚本）还原。
boot 链没动过，所以不需要刷 boot；真砖才走 9008 + QFIL（device type ufs、不勾 format-all）。

## 7. 2026-10-24 真机结果：双补丁仍 900E，**已回滚**

### 7.1 刷入（有设备）

- 设备 `SN-REDACTED-B`，fastbootd（`is-userspace=yes`，slot a，`unlocked=yes`），电量 4.2 V
- 四分区尺寸已是 A17 版（system 1,749,999,616 / product 2,999,996,416 /
  system_ext 1,549,996,032 / vendor_dlkm 58,933,248），**无需 resize**
- 命令：`flash_a17_notz.ps1 -VendorDlkm out\vendor_dlkm_a_notz.img -Wipe -Execute`
- MD5 门禁全部匹配：system `A7F6BDDA…`、product `36ECD08C…`、system_ext `FC0A2A7B…`、
  vendor_dlkm `73D487C4…`（zui16 flavour）
- 四分区写入全部 `OKAY`（system 55 s / product 132 s / system_ext 46 s / vendor_dlkm 2 s）；
  `-w` 清 userdata + metadata；reboot

### 7.2 结果：崩溃更早

- 重启后 **≤10 秒** 就出现 `Qualcomm HS-USB Diagnostics 900E (COM6)`，
  比 2026-10-18 的 ~150 秒**更早**
- 这次 900E **没有**在 ~3 分钟后自行退出（停留 >25 分钟）；
  用 Sahara `HELLO` + `RESET(0x07)` 复位后重新启动，数秒内再次回到 900E
  ⇒ **两次启动一致，可复现**
- 期间 `adb devices` / `fastboot devices` 均不可见（未进入 fastbootd）

### 7.3 补丁确实在镜像里（静态复核）

- `vendor_dlkm_a_notz.img`：`/lib/modules/modules.load` 3,569 B / 218 行；
  第 200 行（0-based 199）为 14 个空格，`tz_log` 命中 **0**；
  **首行仍是 `msm_sysstats.ko`**（未清空，`vendor_modprobe.sh` 的 first_module 逻辑不受影响）
- 与 stock `super_8.img` 逐字节差异仅 **14 字节**
- `system_ext` v2：`/etc/build.prop` = `persist.sys.qseelogd=false`；
  v1/v2 的 inode 号与 `security.selinux` xattr 一致（`u:object_r:system_file:s0`）

### 7.4 回滚与恢复

- 设备可再次进 fastbootd 后执行 `flash_a17_notz.ps1 -Rollback -Wipe -Execute`：
  先缩 product/system_ext、再把 system 扩回 5,493,624,832 B，再刷 `super_4/3/6/8`
  （MD5 门禁），全部 `OKAY`
- 重启后 ZUI16 首次开机约 **4 分 40 秒**出现 adb；`sys.boot_completed=1`；
  uptime 6 分钟、tombstones 0、电量 76%
- **设备已恢复正常**

### 7.5 结论

1. 「去 `tz_log_dlkm` + 关 `qseelogd`」双补丁**没有**救活 A17；崩溃点反而前移
   （≤10 s vs ~150 s），说明 `tz_log_dlkm` 不是唯一/首要崩溃点。
2. 按 §9.1 的判定标准，**A17 在 TB331FC 上仍属结构性不可行**，本轮不改变该结论。〔2026-11-07 更正：本轮只证明**该双补丁方向无效**；「结构性不可行」已撤回，见文末〕
3. 不再在 A17 上加注；回到 **A14 MysticGSI（kit GSI）**路线。〔2026-11-07 更正：此封口判断已撤回，A17 线仍在推进，见文末〕
4. 若将来还要查：优先解析 900E 内存转储，或先用 `diag` 变体抓第一次 tombstone；
   不要再盲目换分区组合重试。
