## 3. vbmeta 决策：不刷

复核 AOSP libavb 源码（`E:\rom\release\tmp\_kern\avb_slot_verify.c`）与 `first_stage_mount.cpp`：

- `avb_slot_verify.c:946-960`：顶层 vbmeta flags 含 `VERIFICATION_DISABLED` 时，遍历描述符（含 Chain Partition → vbmeta_system）全部跳过，`goto out`。
- `first_stage_mount.cpp:805-812` `IsHashtreeDisabled()`：`vbmeta.status() == kHashtreeDisabled || kVerificationDisabled` → `LOG(ERROR) << "Top-level vbmeta is disabled, skip Hashtree setup"` + `return true` → **分区直接挂载，不建 dm-verity**。
- 本机实证：设备当前 `boot_a`（`0b470127…`，kit 的 ZUXOS A15 boot）与 ZUI16 vbmeta 的 boot Hash 描述符（46,841,856 B）**不匹配但照常启动** ⇒ 已处于 kVerificationDisabled 状态。

⇒ **本次实验不刷 vbmeta**，保持原厂 ZUI16 vbmeta（`9466f0e8…`/65,536 B，flags=0）。已备好 `E:\rom\release\tmp\_a17try\vbmeta_a_flags3_zui16.img`（sha256 `5DD06331…`，flags 字节 @0x7B = 0x03）作为备用，未使用。

## 6. 结论与后续

### 6.1 已确认的事实

1. **A17 三镜像刷入后启动失败，掉 900E** —— 现象与历史 T7 一致，但本次是**干净基线 + 未动启动链 + 未刷 vbmeta**，因此可以排除「套件混搭」「super 元数据脏」「vbmeta 不匹配」三个历史假设作为唯一原因。
2. **900E 是 Sahara 崩溃转储模式，firehose/QFIL 接不进**（VID_05C6&PID_900E）；设备会在约 3–7 分钟后自行退出 900E 回到 bootloader fastboot。
3. **`fastboot reboot fastboot` 在 system 不可启动时会失败**（`Failed to boot into userspace fastboot`），但设备随后会自行走到 fastbootd，可用于回滚。
4. **回滚流程可靠**：resize 还原 + 刷 `super_4/3/6.img` + `-w` + reboot，159 s 恢复开机，无需 QFIL/9008。

### 6.2 失败原因排查方向（下次实验）

按「4–8s 回 fastboot=ABL 拒绝 / 30s 后 900E=init 早期失败 / 1–3min=服务死 / 无响应=panic」判层：本次从 reboot 到 900E 约 150 s（含 USB 枚举与多次 PnP 变化），落在「init 早期失败」区间。

排除项：
- ~~vendor api level 门禁~~：AOSP main `property_service.cpp:1135-1138` 是 `LOG(ERROR)` + 回退 `__ANDROID_VENDOR_API_MAX__`，不中止。
- ~~SELinux 策略版本 > 33~~：AOSP init 编译期 `SEPOLICY_VERSION=30`，现场 `secilc -c 30`；A17 CIL 内容也无 >33 专属语句（iomemcon/ioportcon/pcidevicecon/devicetreecon 全 0）。
- ~~vbmeta 校验~~：本机已处于 kVerificationDisabled，dm-verity 不强制。

剩余候选（按可能性排序）：
1. **first stage 挂载失败**：`first_stage_mount.cpp:540 LOG(FATAL) << "Failed to mount required partitions early ..."`。A17 三镜像无 `skip_mount.cfg`，原厂 product/system_ext 会正常挂载；且 fstab 声明 `avb=vbmeta_system` 与镜像尺寸不符。
2. **A17 镜像缺 GSI 兼容层**：A17 三镜像内 `/system_ext/etc/init/config` 不存在（无 skip_mount.cfg）、`/system/mystic`、`/system/phh` 均不存在 —— 与 kit GSI 相比缺整套跨机型适配层。
3. **apex 校验失败**：`apexd.rc` 的 `apexd-bootstrap` 带 `reboot_on_failure reboot,bootloader,bootstrap-apexd-failed`；A17 镜像的 `/bootstrap-apex/` 是空目录，`/system/etc/security/apex` 不存在。
4. **VNDK/LLNDK 符号不兼容**：A17 system 带 `ro.llndk.api_level=202604`，设备 vendor 为 33；虽 A17 镜像已注入 `com.android.vndk.v33.apex`（47,316,992 B），但 A17 的 LLNDK stub 库是否全部满足 v33 vendor 未验证。
5. **BPF 程序**：A17 的 4 个 `.bpf` 依赖 6.6 内核符号（5.15 全无），bpfloader 按名跳过，预计非致命但未实测。

### 6.3 下次实验建议

**方向 A（成本最低）**：给 A17 三镜像补上 kit GSI 那套 GSI 兼容层（`skip_mount.cfg` + Phh 文件层 + vndk.rc + mystic.rc），再刷一次。这是「把 yupei 裸分区改造成可跨机型 GSI」的正路，也是 kit GSI 能启动而 A17 不能的关键差异。

**方向 B（取证优先）**：先不刷机，用「A17 system 镜像 + 原厂 vendor/内核」做离线分析——比对 A17 的 `init.rc` 与 kit GSI 的 `init.rc`、比对两者 `/system/etc/init/` 差异、检查 A17 是否有 vendor 侧缺失的 HAL 声明。

**方向 C（放弃 A17）**〔2026-11-07 更正：这是当时可行的选项之一，但其依据「结构性不可行」已撤回，见文末〕：接受「TB331FC 上澎湃4 结构性不可行」的结论（vendor API level 33 封顶 + 闭源 A13 HAL + 无 A17 BSP），转回澎湃2（A14 MysticGSI）路线。

## 7. 本次实验的教训

1. **`fastboot reboot fastboot` 不是回滚入口**：system 坏掉时它必失败；应等设备自行退出 900E → bootloader fastboot → 再 `reboot fastboot` 或直接等 fastbootd 自现。
2. **900E 的 USB 枚举是间歇性的**：不能凭单次 `Get-PnpDevice` 空结果就判断设备不在；需连续轮询。
3. **回滚不需要 QFIL/9008**：`super_*.img` 可直接 `fastboot flash` 到对应逻辑分区，已第三次验证。
4. **`Invalid sparse file format at header magic` 是正常提示**，fastboot 会自动转 sparse 分片，不是错误。
5. **dtbo 分区尺寸（25,165,824 B）大于 ZUI16 原厂 dtbo.img（8,388,608 B）** —— 该分区此前被扩过，回滚时不要用错尺寸的文件。
