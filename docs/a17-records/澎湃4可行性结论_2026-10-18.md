## 二、任务背景与目标

### 2.1 原始诉求

在 TB331FC 上运行**澎湃 4.0（HyperOS 4，Android 17 底座）**。此前已经完成过一次「完整移植」评估，结论是不可行；但那条结论针对的是**含换内核的完整移植**。用户随后指出：「KMI 直接原版不就好了吗，不然用 GSI 的」——即只换 system 侧、保留原厂内核的**轻量路线**。

这条路线在逻辑上是成立的，因为：

- GSI 本身不含内核，天生跑原厂 KMI；
- TB331FC 是 Treble 设备（`ro.treble.enabled=true`），system 与 vendor 通过稳定接口解耦；
- 因此「能不能跑澎湃 4.0」等价于「A17 的 system/product/system_ext 能不能在这台 A13 vendor 上跑起来」，与内核版本无关。

### 2.2 本报告要回答的问题

1. 只刷 A17 三镜像（system / product / system_ext），保留原厂 boot 链与 vendor，能否启动？
2. 如果不能，**卡在哪一层**？是用户态兼容性、SELinux、VINTF、VNDK，还是内核？
3. 这个卡点是否可绕过？成本多少？
4. 如果不可行，最优替代路线是什么？

## 四、静态可行性核对（刷机前）

> 这一节回答「纸面上能不能过」。所有核对都在 PC 侧离线完成，素材是 A17 源包解包树与设备侧回读。

### 4.1 VINTF / FCM —— **通过**

- A17 的 framework compatibility matrix（FCM）全集 104 项，对照设备 33 个已注册框架 HAL，**违规 0**。
- 横向对照：kit GSI 94 项 / 33 HAL、ZUI16 93 项 / 33 HAL，违规同为 0。
- 反向 DCM（device compatibility matrix）少列 12–15 个 HAL，但 VINTF 只对 FCM 做硬校验，DCM 缺项非硬门。
- `ro.vendor.api_level` 由 init 在启动时按 `ro.board.first_api_level` / `ro.board.api_level` / `ro.product.first_api_level` 计算得出 33（`property_service.cpp:1107-1144`，`property_initialize_ro_vendor_api_level()`），不是编译期常量。

**结论**：VINTF 不是卡点。

### 4.2 SELinux —— **通过**

- 设备 `/vendor/etc/selinux/plat_sepolicy_vers.txt` = `33.0`（5 B）。
- A17 携带 `mapping/33.0.cil`（150,588 B）+ `33.0.compat.cil`（1,412 B），可做策略映射。
- 符号缺口 0，与 kit GSI 同档。
- 已捕获的 A17 启动日志里 `init: Compiling SELinux policy` 是**成功**日志，不是 FATAL（该日志来自 §6.1 的崩溃转储，会话属性见 §6.4 第 3 条限定）。

**结论**：SELinux 不是卡点。`getenforce=Enforcing` 状态下也没有 avc 拒绝导致启动中止的记录。

### 4.3 BPF —— **低风险**

A17 `/system/etc/bpf` 有 4 个已编译 `.bpf` + 5 个子目录，bpfloader 按名加载、找不到则跳过；kit GSI 同样带 BPF 且能启动。

**结论**：非阻断。

### 4.4 mi_ext —— **不需要刷**

A17 全部 rc / prop 中引用 mi_ext 的行数为 0，它只是空挂载点；设备也没有 mi_ext 分区。

**结论**：非阻断。

### 4.5 ELF 闭包 —— **0 真缺口**

- 扫描 4,053 个文件 / 1,312 个 ELF64，12 个 soname 由 APEX 提供（属正常 APEX 内闭包），`libcryptfs_hw.so` / `libmisight.so` 由 system_ext 自带，`libnetd_*` 在 `.capex` 嵌套层。
- `dumpstate` 的 `DT_NEEDED` 里含 `libmiuidumpstate.so`，system_ext 的 `lib/` 与 `lib64/` 均有提供。

**结论**：不存在「少一个 so 就起不来」的缺口。

### 4.6 rc 审计 —— **非阻断**

- 164 个 service 定义，99 个被 start。
- 仅 3 个缺二进制：`adbd`（disabled + APEX 覆盖）、`traced_relay`（disabled）、`mqsasd`（无 critical 标记）。
- 10 个 `critical` 服务的二进制**全部在位**（servicemanager、hwservicemanager、vold、lmkd、keystore2、mmd、blank_screen 等）。
- `init.zygote64_32.rc` 里定义的是 `zygote_secondary /system/bin/app_process32`；zygote 本体在 `init.zygote64.rc` 的 `/system/bin/app_process64`（51,856 B，在位）。

### 4.7 分区空间 —— **可解**

以 10-18 实验**实测**（`fastboot getvar partition-size`，与回滚用的 `super_4/3/6.img` 尺寸一致）为准：

| 分区 | 实测原尺寸 (B) | 目标尺寸 (B) | 变化 |
|---|---|---|---|
| system_a | 5,493,624,832 | 1,749,999,616 | −3,743,625,216 |
| product_a | 594,411,520 | 2,999,996,416 | +2,405,584,896 |
| system_ext_a | 460,103,680 | 1,549,996,032 | +1,089,892,352 |
| 合计 | 6,548,139,712 → 6,299,992,064 | — | super 组上限 12,876,513,280，余约 6.12 GiB |

> 口径说明：10-13 构建归档 `ARCHIVE-2026-10-13-a17-three-ext4-rebuild.md` §6.3 记的是 system_a 5,852,708,864 / product_a 756,654,080 / system_ext_a 653,033,472（合计 7,262,396,416），与 10-18 实测不同。原因是两次记录之间设备 super 布局已变（10-13 之后做过 GSI 刷写与回滚）。**以 10-18 实测为准**，它才是本次实验的实际输入。

**结论**：空间充裕。resize 有严格顺序——**刷入时先缩 system 腾出空间，再扩 product / system_ext**；**回滚时反过来，先缩 product / system_ext 再扩 system**。顺序错会因组内空闲不足而失败。

### 4.8 两段式 init —— **接口稳定，不需要换 boot**

- 第一段 = init_boot ramdisk 里的 A15 init（KSU 包装：`init` + `init.real` + `kernelsu.ko`）→ **不动**。
- 第二段 = `/system/bin/init`（A17，2,773,056 B）→ 被替换。
- 两段之间的接口是 AOSP 稳定 ABI（`init` → `second stage` 的 `exec`），不需要换 boot / init_boot / vendor_boot。

### 4.9 静态核对小结

纸面上**没有一条硬门被触发**：VINTF、SELinux、BPF、mi_ext、ELF 闭包、rc、空间、init 两段式全部通过或可解。因此才值得做真机实验——这正是 10-18 实验的前提。

## 五、真机实验：干净基线三镜像刷入（2026-10-18 15:00–15:31）

完整记录见 `E:\rom\docs\实验记录_A17三镜像干净刷入_2026-10-18.md`。要点：

### 5.1 实验设计

- **干净基线**：此前所有 boot loop 排查都动过启动链（KSU、init_boot、vbmeta）。这次**不动启动链、主动不刷 vbmeta**，只替换 system / product / system_ext 三个逻辑分区，把变量降到最少。
- **vbmeta 决策依据**：
  - `avb_slot_verify.c:946-960`：`VERIFICATION_DISABLED` 时跳过全部描述符校验；
  - `first_stage_mount.cpp:805-812` `IsHashtreeDisabled()` 返回 true 时分区直接挂载、不建 dm-verity；
  - 本机 boot Hash 与 vbmeta 不匹配仍能正常启动 ⇒ 已处于 `kVerificationDisabled`。
- 备份启动链 6 件 → `E:\rom\release\tmp\_a17try\chain_backup\`。

### 5.2 执行

1. `adb reboot fastboot` → fastbootd（`is-userspace: yes`）。
2. resize：system 5,493,624,832 → 1,749,999,616（先缩），product 594,411,520 → 2,999,996,416，system_ext 460,103,680 → 1,549,996,032（后扩），三条 OKAY，新尺寸 `0x684EE000` / `0xB2D05000` / `0x5C631000`。
3. 刷入：system 6 片 73.2 s、product 11 片 124.9 s、system_ext 6 片 90.1 s，全 MD5 match。
4. `fastboot -w` 擦 userdata + metadata。
5. 15:14:41 reboot。

### 5.3 结果

- t+0–120 s：adb / fastboot 均无响应。
- **t+~150 s：出现 `Qualcomm HS-USB Diagnostics 900E (COM6)`（USB\VID_05C6&PID_900E\5E367954）**，间歇性枚举。
- **15:21:47：900E 自行退出 → bootloader fastboot（`is-userspace: no`）**。

### 5.4 回滚

1. `fastboot reboot fastboot` 失败：`Failed to boot into userspace fastboot; one or more components might be unbootable.` ← **这是「系统不可启动时无法直接进 fastbootd」的实证**，回滚入口不是它。
2. 等约 2 min，设备自行进 fastbootd。
3. resize 还原（先缩 product/system_ext 再扩 system，尺寸回 `0x147721000` / `0x236E0000` / `0x1B6CA000`）。
4. 刷 `super_4.img`（21 片 214.9 s）/ `super_3.img`（3 片 19.5 s）/ `super_6.img`（2 片 15.7 s）+ `-w` + 15:29:00 reboot。
5. **15:31:45 adb 上线**：`boot_completed=1`、`incremental=TB331FC_CN_OPEN_USER_Q00003.0_U_ZUI_16.0.544_ST_241115`、system_server PID 1777、zygote64 PID 871、电池 86%。

### 5.5 本次实验已排除的假设

| 假设 | 排除依据 |
|---|---|
| 套件混搭 / super 分区脏 | 本次是干净基线，只换三个逻辑分区 |
| vbmeta 校验不通过 | 未刷 vbmeta，且设备已处 VERIFICATION_DISABLED |
| vendor api level 门禁启动即中止 | A17 init 实际跑到 second stage（见 §7.3 日志） |
| SELinux 策略版本 > 33 | A17 SEPOLICY_VERSION=30，且现场编译成功 |
| 分区空间不足 | 6.30 GB ≪ 12.88 GB 组上限 |

**剩余候选（本次实验未能区分，由 §6 的崩溃取证进一步收敛）**：

1. first stage 挂载失败（`first_stage_mount.cpp:540` `LOG(FATAL)`；A17 无 `skip_mount.cfg`；fstab 里 `avb=vbmeta_system` 与镜像尺寸不符）；

3. apex 校验失败（`apexd-bootstrap` 带 `reboot_on_failure reboot,bootloader,bootstrap-apexd-failed`；`/bootstrap-apex/` 为空目录）；
4. VNDK / LLNDK 符号不兼容（`ro.llndk.api_level=202604` vs vendor 33；已注入 `com.android.vndk.v33.apex` 但未验证）；

### 6.3 寄存器与符号解析

`krunqueue_text.txt` 内容：`DIE CPU : 3`、`PC: 0xffffffe8926963bc`、`LR: 0xffffffe88d978200`、`SP: 0xffffffc00f09bb80`，附 PC/LR 各 64 个 32-bit 指令字与 SP/X0/X1 内存转储（X1 区 `********` 不可读）。

解析步骤：

1. **PC 定位**：PC 的 32 字节指令模式在 `vmlinux_149.elf` 文件 offset 615,804（0x9657C）**唯一命中**，映射 vaddr `0xffffffc0080963bc`；与运行时 PC 相差 `0x288a600000`（KASLR 偏移）。
2. **PC 符号**：用 ELF `.symtab` 二分 → **`PC = __memcpy_fromio+0xb0`**（函数起点 `0xffffffc00809630c`；邻居 `__memset_io` 0x…96048、`__memcpy_toio` 0x…96190、`vvar_fault` 0x…9649c）。函数体是 `ldrb w8,[x8]` / `strb w8,[x0,#4]` 的字节搬运循环——**与 synchronous external abort（读非法 MMIO）完全吻合**。
3. **LR 定位**：LR 的 32 字节模式在 vmlinux 中不命中，在 `tz_log_dlkm_zui16.ko` 文件 offset 8,704（0x2200）**唯一命中**。模块 `.text` 段 `off=0x2000 addr=0x0 size=0x21d4` ⇒ 模块内偏移 `0x200`，模块加载基址 = `0xffffffe88d978000`。
4. **LR 符号**：模块 `.symtab` 二分 → **`LR = tzdbg_fs_read+0x88`**（`tzdbg_fs_read` vaddr `0x178`，size `0xd1c`；同模块另有 `tzdbg_procfs_open` 0x138/0x40、`tzdbg_procfs_release` 0xe94/0x24、`_disp_log_stats` 0xeb8、CFI jump table `tzdbg_fs_read…cfi_jt` 0x100）。
5. **指令级复核**：`tzdbg_fs_read` 序言 `0x178 paciasp / 0x17c sub sp,sp,#0xa0 / 0x1a0 ldr x8,[x0,#0xd8] / 0x1a4 cbz x8,#0x3bc / 0x1c0 ldr w22,[x8]`；`0x200` 处是 `ldr x1,[x8]`（位于分支目标 `0x27c` 之前），即 LR 恰为该 `bl` 之后的返回点。

**结论链闭合**：

```
/proc/tzdbg/* read  →  tzdbg_fs_read（tz_log_dlkm）
                    →  __memcpy_fromio（内核）
                    →  FAR 0xffffffff96000210 非法 MMIO
                    →  synchronous external abort
```

**与模块自报日志一致**（`090_md_KWDOGDATA.BIN.bin` offset 95,568，带 uptime 可采信）：

```
[5.750110][ T167] tz_log_dlkm:[tzdbg_get_tz_version][1746]: tz diag version is 2403000
[5.750146][ T167] tz_log c125720.tz-log: RM log address is not defined
[5.750193][ T167] tz_log_dlkm:[tzdbg_query_encrypted_log][1780]: encrypted qseelog enabled is 0
[5.750208][ T167] tz_log_dlkm:[tzdbg_init_tme_log][1415]: Tme Crashdump address offset need to be defined!
[5.750212][ T167] tz_log_dlkm:[tz_log_probe][1891]: Tme log initialization failed!
```

即：**模块自己在 probe 阶段就报告「RM log 地址未定义」「Tme crashdump 地址未定义」「Tme log 初始化失败」，但并没有禁用 `/proc/tzdbg/*` 的读路径**；后续有进程读 `/proc/tzdbg/log`（或 `qsee_log`）时，`tzdbg_fs_read` 拿未定义地址去 `__memcpy_fromio`，直接触发外部中止。

### 6.4 三条必须写明的限定（证据强度）

1. **没有内核栈文本**。`rawdump_full.bin` 扫描 `Comm:`=0、`Call trace`=0、`pc :`=0、`Unable to handle`=0、`tzdbg_fs_read`=0、`proc_reg_read`=0、`__memcpy_fromio`=0；`oops_full.txt` 的 `Internal error` 之后 5,000+ 字符全为空白。`krunqueue_text.txt` 只有寄存器。**因此「PC/LR 落在哪」是反汇编闭合的，不是栈回溯读出来的。**

3. **这次崩溃不是 10-18 干净基线实验**。证据：
   - 崩溃会话内核串为 **5.15.149**（= ZUI17 的 boot），而 10-18 实验的 `chain_backup/boot_a.img` 是 **5.15.167**（= kit boot）；

   - 现存所有 boot/vendor_boot 备份均不含 `permissive`。
   - ⇒ 该 dump 来自**更早一次人为关闭 SELinux 的排障会话**，其结论不能直接等同于 10-18 干净基线；但 dump 内容含 `CP2A`(4 处)、`missi`(101 处)、`370399999`(26 处)、`vndk`(12 处)、`apexd`(300 处) 等 A17 专有标记（`rawdump_full.bin` 全盘计数），**确认其确为「A17 系统镜像 + 5.15 内核」会话**。

### 6.5 与 900E 的时序一致性

- 崩溃点 33.05 s → 内核 panic → 进入 Sahara 崩溃转储模式 → 主机侧约 150 s 后枚举到 `900E`。

### 7.1 三组属性对照

| 设备（ZUI16 vendor） | 33 | （空） | 33 | Android 13 / GKI 5.15 |
| A17 源包 **vendor 分区** | **202404** | — | **35** | Android 15 / GKI 6.6 |
| A17 源包 **system 分区** | 33（继承值） | **202604** | — | Android 17 / GKI 6.18 |
| kit GSI（A14） | — | 无 | — | Android 14 / SDK 34 |

**这是本报告最重要的修正**：旧结论说「设备 vendor 33 vs A17 要求 202604」，方向对但对象错——A17 的 **vendor 分区自己就声明了 202404**，说明它不是「一个 A17 系统跑在 A13 vendor 上」，而是「一个 A15 vendor 世代 + A17 system 世代的组合包」。把这样的系统塞进 A13 vendor，跨的是 2 代 vendor API level，而不是 1 代。

### 7.3 修正：vendor API level 门禁**不会**在启动早期中止

旧会话（`session-a1c5aa16` T11）曾反汇编 A17 init，定位到 `0x0f627c` 读 `ro.vendor.api_level`，默认常量 `0x0F4240 = 1,000,000`，与 `ro.build.version.sdk`（`w21=0x2710=10000`）比较，失败则 `bl #0x282378` 且 `w0=4`，据此判断「门禁不通过即中止启动」。

本次复核推翻了这个推论：

- AOSP `property_service.cpp:1135-1138` 的实现是 **`LOG(ERROR)` + 回退 `__ANDROID_VENDOR_API_MAX__`**，不是 `LOG(FATAL)`；
- 现场日志反证：A17 init **实际跑到了 second stage**——
  - `init: Opening SELinux policy` → `init: Compiling SELinux policy`（成功）
  - `apexd: Started. subcommand = --bootstrap`
  - `apexd-bootstrap: Found pre-installed APEX /system/apex/com.android.vndk.v33.apex`（**我方注入件被识别**）
  - `servicemanager: Starting sm instance on /dev/binder`
  - `vold` / `fsck.f2fs` 完成（`vdc()++ checkpoint needsCheckpoint`）
  - `hypsys_ssi` 已在查询 VINTF（`IHypSysSsi/default`、`Intl/default`），并对 `vendor.xiaomi.hardware.misys.common.IMiSysImpl` 报 avc denied
- 若门禁在 early init 中止，上述日志全部不可能出现。

**修正后的结论**：vendor API level 33 vs 202404/202604 是**结构性不兼容的根因**（决定了下游大量行为差异），但它**不是**「一行代码把你挡在门外」的硬门。真正的失败是**下游的内核态崩溃**（§6）与**世代错配引发的服务级不兼容**。

## 八、为什么「只刷 system」这条路也走不通

### 8.1 逻辑回顾

用户提出的路线是对的：GSI 不含内核，跑原厂 KMI，所以「换 system」在原理上可行。kit GSI（A14 MysticGSI）历史上确实在这台机器上启动成功过，证明这条路本身成立。

问题在于**澎湃 4.0 的 system 不是 GSI**：

| 对比项 | kit GSI（A14 MysticGSI） | 澎湃 4.0 三镜像（A17） |
|---|---|---|
| Android / SDK | 14 / 34 | 17 / 37 |
| 与设备 vendor 的代差 | 1 代（33→34） | 2–3 代（33→202404/202604） |
| 是否含 GSI 兼容层 | 是（`/system/phh`、`/system/mystic`、`/system_ext/etc/init/config`） | **否** |
| VNDK 形态 | 自带 v33 全套 | 36 个 apex 中**无任何 `com.android.vndk.*`**（只有 system_ext 的 v34） |
| 是否假设 vendor 是 A15+ | 否 | **是**（vendor 分区 202404、`ro.board.api_frozen=true`） |
| 内核要求 | 原厂 5.15 即可 | 名义上 6.18，实测 5.15 上崩溃 |

**核心判断**：澎湃 4.0 是**完整 ROM 移植包**，它的三镜像之间、以及它与 vendor 之间是一个**版本封闭的集合**。把它拆成「只刷 system 侧」时，丢掉的不只是内核，还有 vendor 分区那一半的世代信息。kit GSI 之所以能跑，正是因为它**专门为「跑在别人的 vendor 上」而设计**——它自带兼容层、自带 VNDK、把对 vendor 的假设降到最低。

### 8.2 三条路线评估

| 路线 | 内容 | 成本 | 成功率 | 结论 |
|---|---|---|---|---|
| **A** | 给 A17 三镜像补 kit GSI 兼容层（`skip_mount.cfg` + Phh 文件层 + `vndk.rc` + `mystic.rc`）再刷 | 中（2–3 天） | 低 | 兼容层能解用户态问题，**解不了内核态 MMIO 崩溃**（§6）。除非同时关掉 qseelogd/tzdbg 读取路径 |
| **B** | 离线取证：逐项比对 A17 init.rc 与 kit GSI、`/system/etc/init/` 差异、vendor HAL 声明，把「还差什么」列全 | 低（半天） | — | **推荐作为收尾动作**，但产出只是清单，不是可用系统 |
| **C** | 放弃 A17，转 A14 MysticGSI | 低（1 小时，含 `fastboot -w`） | **高（已验证）** | **推荐** |

### 8.3 为什么 A 路线不推荐

即使把用户态兼容层补齐，仍然要面对：

1. **内核态崩溃**（§6）：`tzdbg_fs_read` → `__memcpy_fromio` 的非法 MMIO 是内核模块行为，用户态补丁改不了；只能靠「不触发」（关 qseelogd、改 system_ext build.prop）绕开，而这只解决一个点，不解决「A17 system 假设 A15+ vendor」的全局问题。
2. **vendor HAL 缺失**：`vendor.xiaomi.hardware.misys.common.IMiSysImpl` 这类 A17 system_ext 强依赖的 vendor HAL，A13 vendor 里根本没有，且 vendor 闭源无法补。
3. **投入产出比**：每条兼容层补丁都要真机刷一次验证，而每次失败都要走 3–7 min 的 900E 等待 + 完整回滚（约 15 min）。在 2 核 896 Mi 的服务器上做远程验证更慢。

## 九、最终结论

### 9.1 直接回答

〔⚠️ 2026-11-07 更正：本条已撤回，见文末「更正」节〕**澎湃 4.0（A17）在 TB331FC 上不可行，不是「难」，是「结构性不可行」。**

**但 §10.4 的 raphael 反例表明，这个结论仅适用于 TB331FC 的具体硬件组合，不能推广为「A17 在任何老 vendor 上都不可行」。** 真正卡住 TB331FC 的不是 vendor API level 33 这个数字，而是 TB331FC 特有的内核模块 `tz_log_dlkm` 与 A17 用户态的冲突。

理由三条，按重要性排序：

1. **世代错配不可修补**：A17 包的 vendor 分区自报 vendor API level 202404（A15/GKI 6.6），system 要求 202604（A17/GKI 6.18）；设备 vendor 停在 33（A13/GKI 5.15）。vendor 分区闭源，无法把设备拉到 A15+ 世代。
   - **例外（§10.4）**：raphael（vendor API 30，内核 4.14.357）正常运行 A17 system，说明「vendor API 33 vs 202604」不是硬门。
2. **内核态崩溃无法用用户态手段解决**：已捕获的崩溃是 `tz_log_dlkm:tzdbg_fs_read` → `__memcpy_fromio` → synchronous external abort（§6）。这是 5.15 内核模块的行为，A17 用户态镜像改不动。
   - **例外（§10.4）**：raphael 的 4.14 内核没有 `tz_log_dlkm`、没有 `/proc/tzdbg`，无从崩溃。
3. **A17 不是 GSI**：它没有 GSI 兼容层，天然假设一个同世代的 vendor。把它当 GSI 用，等于只搬了一半的系统。
   - **例外（§10.4）**：raphael 的 vendor 也是老一代（Android 11），但 system 自带 VNDK v30 apex + SELinux 映射到 34/202604，能正常启动。

**修正后的结论**：A17 system 在 TB331FC 上不可行，根因是 `tz_log_dlkm` 模块在地址未定义时仍可读、读取即崩内核。若能黑名单或移除该模块，A17 方向**可以继续投入**（§10.4 末）。

### 9.3 已知的 kit GSI 遗留问题

历史上刷 kit GSI 时出现过 boot loop，根因已定位并修复：

- **根因**：PID1 fd 泄漏。`kai_init.sh` 在 `/dev/kmsg` 不存在时执行 `exec 3>>/dev/kmsg`，创建了一个普通文件，`readlink /proc/1/fd/3` 变成 `/null`；`system_server` 启动时 `FileDescriptorInfo::CreateFromFd` 撞上 `Not allowlisted (3): /null`，JNI FatalError 崩溃，每约 5 秒一次。
- **当时的修复**：`fastboot flash init_boot_a ib_patched.img`（sha256 `F18DC14A…D68B152`）。该镜像**没有 stage1 脚本**（`init.real` 就是 AOSP init），因此结构上不可能产生 stray fd。设备现役 init_boot 就是它，实测 `/proc/1/fd` 无 `/null` 型描述符。
- **修正版的两次迭代（2026-10-18 晚）**：
  - `kai_init_v5_FIXED.sh`（752 B）**作废，不可刷**。它在 stage1 做 `eval "exec $i>&-" 2>/dev/null`，而 stage1 时 `/dev` 还是 init_boot ramdisk 里的空目录（cpio 中 `dev` 是 mode 0755 的空目录，`/dev/null` 不存在，rootfs 由 tmpfs 支撑）。
  - **v5 的实测失效机制（设备 chroot 复现，空 `/dev`、无 `/proc`，busybox 1.36.1）**：
    - `2>/dev/null` 里的 `/dev/null` 被**当成普通文件创建**；
    - 循环在 i=10 时关闭了 busybox ash 读取脚本所用的 fd 10，shell 随即反复报 `/init.real: line 20: 10: Bad file descriptor`，而该 stderr 又被追加进那个假的 `/dev/null`；
    - 结果是一个**失控循环**：2 s 内假 `/dev/null` 长到 11,725,347 B、5 s 内 28,084,611 B，`exec /init.bin` **始终未被到达**，进程被 timeout 杀掉（rc=137）。
    - ⇒ 刷进去的后果不是 boot loop，而是 **init 永不启动 + rootfs(tmpfs) 被垃圾文件灌满内存**，比原 boot loop 更难救。同理 `[ -c /dev/kmsg ]` 在 stage1 恒为假，其 `KAI_V5 boot` 标记永远写不出。
  - `kai_init_v6.sh`（709 B，sha256 `033F8173…1879701`）是修正版：只做 fd 卫生（`while [ $i -le 255 ]` 逐个 `exec $i>&-`，**零 I/O、零重定向、不碰 /dev 与 /proc**），最后 `exec /init.bin`。**同一套 chroot 复现环境下对比**：v6 用时 ≤1 s、`rc=0`、正常到达 `/init.bin`（输出 `REACHED_INIT_BIN`）、**不创建 `/dev/null`**；v5 两次（2 s / 5 s）均 rc=137、未到达。另在真机上用 busybox 实测：关 3–255（含预先打开的 3/7/42/200）后 shell 存活并继续执行；两段式 `exec busybox sh -c` 场景同样成立。
  - v6 镜像 `E:\rom\release\tmp\_ibv5\ib_v6.img`（8,388,608 B，MD5 `99F19D9246195EB817F0CC703982FFBE`，SHA256 `2B61A029…7BA171`）已构建并静态验证：22 个 cpio 条目齐全且顺序不变，只替换 `init.real` 内容，ramdisk 之后到文件末尾与 `ib_copier`/`ib_patched` **逐字节相同**，AVBf footer 原样保留。**尚未刷入**。
- **结论**：若目的只是避免 fd 泄漏 boot loop，**继续用 `ib_patched.img` 即可**（无 stage1 脚本 = 无泄漏面）。v6 只在确实需要 stage1 挂钩（例如要在 early init 阶段落盘取证）时才值得刷，且刷它属于额外风险，不是必需项。
- **另一个已存在的差异（观察项，非阻断）**：kit 原厂 init_boot 的 ramdisk 含 `lib/firmware/novatek_ts_fw.bin`（196,608 B 触控固件），而我们所有 KSU 变体（`ib_patched` / `ib_copier` / `ib_v5` / `ib_v6`）的 cpio 里都**没有**这个文件（原厂 20 条 vs 我方 22 条，多的是 `busybox`/`init.bin`，少的是 `lib/` 整支）。设备当前用 `ib_patched` 触控正常，说明该固件可由 vendor 侧提供或非必需，但重打包时若要完全对齐原厂形态，应把 `lib/firmware/novatek_ts_fw.bin` 一并加回。

### 9.4 持久化 kernellog 给出的独立佐证（2026-10-18 晚新增）

设备 `/data/local/newlog/aplog/kernellog*` 有 6 个轮转文件（共 22.9 MB），是**掉电也不丢**的持久化内核日志。把它们按「每次 `Booting Linux` 切分」后逐会话统计，得到 §9.3 结论的**第二条独立证据链**（第一条是 10-17 会话里的 `readlink /proc/1/fd/3` + tombstone）。

| 文件 | 行数 | boot_completed | system_server | `starting zygote` | `zygote received signal 6` | `avc … path="/null"` | 判定 |
|---|---|---|---|---|---|---|---|
| kernellog | 23,971 | 21 | 1,081 | 1 | 0 | 0 | OK |
| kernellog.1 | 8,106 | 22 | 1,073 | 1 | 0 | 0 | OK |
| kernellog.2 | 13,661 | 21 | 1,144 | 1 | 0 | 0 | OK |
| **kernellog.3** | **62,230** | **0** | **0** | **389** | **389** | **3,685** | **boot loop** |
| **kernellog.4** | **77,301** | **0** | **0** | **516** | **515** | **4,836** | **boot loop** |
| kernellog.5 | 9,904 | 21 | 1,000 | 1 | 0 | 0 | OK（含 `KAI_SELF` 标记 1 条） |

三条可直接引用的事实：

1. **这 6 个会话全部是我方 KSU init_boot 启动**，不是原厂固件记录。每个文件都有同一段启动头：`ksuinit::init[1]: Hello, KernelSU!` → `load kernelsu with params "allow_shell=1"` → `KernelSU: welcome to KernelSU version 33355` → `KernelSU: shell is allowed at init!` → `ksuinit::init[1]: init is init.real`。其中 `ksuinit` 是我方 KSU wrapper 的日志前缀，`allow_shell=1` 直接来自我方 `ksu_config`（13 B）。**原厂固件不可能出现这些标记**，所以 kernellog 记录的是我们自己的刷机实验，此前「疑似产线日志」的判断已推翻。
   - 进一步按第二段 init 的日志标签可分**两代 ramdisk**：`kernellog` / `.1` / `.2` 的标签是 `init:`（第二段 init 以 `init` 为程序名启动，属**无 stage1 脚本**的形态）；`kernellog.3` / `.4` / `.5` 的标签是 `init.bin:`（第二段 init 由 stage1 脚本 `exec /init.bin` 拉起）。后者才带 `KAI_` 标记（仅 `.5` 有 1 条 `KAI_SELF pid=130 ctx=[kernel] root=[…]`），前者 `KAI_` 恒 0。
2. **boot loop 的指纹与 §9.3 完全一致**：`kernellog.3/.4` 各只有 1 次启动、`boot_completed` 恒 0、`system_server` 0 命中，但 `starting service 'zygote'` 389/516 次、`Service 'zygote' (pid N) received signal 6` 389/515 次，且 `avc: denied { use } … path="/null" dev="selinuxfs" ino=23 tclass=fd` 3,685/4,836 次。被拒的 `comm` 依次是 `boringssl_self_`、`qseecomd`、`sh`、`vdc`、`cameraserver`、`mediaserverwrap`、`wificond`、`netd`、`android.hardwar`、`app_process32/64`、`audioserver` —— **所有继承 PID1 fd 表的子进程都在 `{ use }` 同一个 `/null` 描述符**，正是 `FileDescriptorInfo::CreateFromFd` 拒绝的那个对象。而 4 个正常会话该计数为 **0**。
3. **同一代 ramdisk 既能正常启动也能 boot loop**：`.5` 与 `.3/.4` 的启动头逐行相同（都是 `init.bin:` 标签、都有 `KAI_` 能力），`.5` 却正常起完（`boot_completed` 21、`system_server` 1,000、`zygote` 只启动 1 次），`.3/.4` 则无限 loop。⇒ loop 的触发因素**不是 init_boot 结构本身，而是某一次启动里多出来的 pre-policy stray fd**——这与 §9.3 的「stage1 脚本在 `/dev` 尚未就绪时创建普通文件」机制吻合；同时也说明**并非所有 stage1 脚本都会泄漏**（`.5` 那版就没有），泄漏取决于脚本具体写法。

两条必须写明的限定：

- **`/null` 是 SELinux 对「policy 载入前打开的 fd」的表示**（`dev="selinuxfs" ino=23`），不是磁盘上真有一个叫 `/null` 的文件。它证明该描述符是**内核 first stage、SELinux policy 载入之前**创建的——这正是 stage1 脚本会做的事，也解释了为什么用户态（policy 载入后）无法用常规手段修复它。
- **无法从 kernellog 反推当时 ramdisk 里是哪个 `init.real`**：`.3/.4` 里 `KAI_` 标记为 **0**（`kernellog.5` 有 1 条 `KAI_SELF pid=130 …`）。这与「脚本把标记写进了假的 `/dev/kmsg` 普通文件、从未到达真内核日志」一致，但**不能作为脚本版本的证据**。同理，`kernellog` 的时间戳不可用于定位日期：设备 RTC 停在 2024-11-15（`date` 实测 `Fri Nov 15 12:57:27 CST 2024`，而 PC 是 2026-10-18），文件里 `Nov 15 2024` 全是坏时钟；`.3/.4` 的 audit 序号连续递增无回退，但 audit 的 epoch 同样落在 2024-11-15 量级。**轮转序只能按每文件首行时间戳排，不能按文件名序号**（实测 `.3`=05:52、`.4`=21:24，序号与时间不单调）。

- raphael：`/system_ext/apex/com.android.vndk.v30.apex`（114,737,152 B）—— **system 镜像自带的 VNDK apex 版本 = vendor 的 `ro.vndk.version`(30)**
- 本项目给 TB331FC 注入的是 `com.android.vndk.v33.apex`（47,316,992 B，来自 kit GSI）
- ⇒ 机制是「system 侧按目标 vendor 的 VNDK 版本配 apex」，不是「A17 必须有 v37」

**SELinux 映射覆盖**：

- raphael `/system/etc/selinux/mapping/` 含 `30.0.cil`(126,395 B)/`30.0.compat.cil`(2,849)、31.0、32.0、33.0、34.0、`202404`/`202504`/`202604` 各一对
- 无 `plat_sepolicy_vers.txt`（新版本用 sha256 文件 `plat_sepolicy_and_mapping.sha256`，65 B）
- `plat_sepolicy_genfs_202504.cil`/`202604`/`202704` 三个 genfs 补丁都在

**崩溃点差异（最关键）**：

- **TB331FC**：5.15 内核有 `tz_log_dlkm` 模块 → 创建 `/proc/tzdbg` → A17 用户态（`qseelogd`/`hypsys_system`/`libmiuidumpstate.so`）读取 → `tzdbg_fs_read` → `__memcpy_fromio` → synchronous external abort（§6）
- **raphael**：4.14 内核**没有** `tz_log_dlkm`、**没有** `/proc/tzdbg` → 同一套 A17 用户态无从读取 → 无崩溃
- raphael 上 `init.svc.qseelogd=stopped`（即使 `persist.sys.qseelogd=true`）—— qseelogd 试图读 `/proc/tzdbg/qsee_log` 时 ENOENT，进程退出，不会崩内核

**修正结论**：

本报告 §9.1 的三条理由需限定适用范围——它们在 **TB331FC 的具体硬件组合（5.15 内核 + tz_log_dlkm + vendor API 33）** 下成立，但**不能推广为「A17 在任何老 vendor 上都不可行」**。raphael 证明：

1. **vendor API level 30 可以跑 A17 system**（不是 33，更不是 202604）
2. **内核 4.14.357（非 GKI）可以跑 A17 system**（不需要 5.15，更不需要 6.6/6.18）
3. **真正的卡点是 TB331FC 特有的内核模块 `tz_log_dlkm`**——它的 `/proc/tzdbg` 接口在地址未定义时仍可读，读取即触发 `__memcpy_fromio` 崩溃
4. **§6.6 H1（qseelogd 读 tzdbg 触发崩溃）从「弱」升级为「中强」**——raphael 是反向对照组（无 tzdbg 无崩溃），但**尚未在 TB331FC 上直接证实**（需关闭 qseelogd 重刷，即 §10.1 #2 的实验）

**对 TB331FC 移植路线的影响**：

- **停止把 vendor API level 33 当作不可逾越的门槛**——它不是
- **优先排查 `tz_log_dlkm` 模块能否黑名单/删除**——如果能从 vendor 模块列表里去掉它（`/vendor/lib/modules/modules.load` 移除 `tz_log_dlkm.ko`），A17 的崩溃链可能直接消失
- **A17 方向可以继续投入**，但前提是先解决 tz_log_dlkm 问题（黑名单/删除/或 patch 模块让地址未定义时返回错误而非继续读）
